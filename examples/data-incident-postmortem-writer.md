# data-incident-postmortem-writer 示例

## 适用场景

数据任务、指标、看板或补数出现事故，需要沉淀一份清楚的复盘材料。

## 示例输入

```text
请用 data-incident-postmortem-writer 写一份数据事故复盘。

事故：电商经营看板 2026-05-20 的 GMV 比真实值少算约 18%。
发现方式：运营在 2026-05-21 10:20 反馈看板与订单后台不一致。
影响范围：
- 经营日报
- 渠道 GMV 看板
- 类目 GMV Top 10
- 影响 2026-05-20 分区

初步原因：
- 订单明细表新增 pay_status = partial_refund 状态
- 看板 SQL 只统计 pay_status = success
- 业务口径要求 partial_refund 订单仍计入支付 GMV，但退款金额应单独扣减

时间线：
- 2026-05-21 10:20 运营反馈异常
- 2026-05-21 11:10 数据开发定位到状态枚举变更
- 2026-05-21 13:40 修复 SQL 并补数
- 2026-05-21 14:10 业务确认恢复

希望输出：面向数据团队内部复盘，同时给业务方一段同步口径。
```

## 预期输出

```markdown
# 数据事故复盘：经营看板 GMV 少算

## 1. 摘要

2026-05-20 分区的经营看板 GMV 少算约 18%。事故由订单支付状态新增枚举后，下游看板 SQL 未同步更新导致。

## 2. 当前状态

已于 2026-05-21 13:40 修复 SQL 并补数，14:10 经业务确认恢复。

## 3. 影响范围

| 影响对象 | 影响时间 | 影响程度 | 处理状态 |
| --- | --- | --- | --- |
| 经营日报 | 2026-05-20 | GMV 少算约 18% | 已修复 |
| 渠道 GMV 看板 | 2026-05-20 | 渠道交易额偏低 | 已修复 |

## 4. 根因分析

直接原因：看板 SQL 只统计 success，未包含 partial_refund。

深层原因：订单状态枚举变更没有触发下游口径影响评估。

机制缺口：缺少枚举值变更监控、指标口径回归测试和上游变更通知机制。

## 5. 预防措施

- 为 pay_status 增加枚举值变化监控。
- 为 GMV 核心指标增加订单后台对账规则。
- 上游订单状态变更必须同步数据团队并评估下游影响。

## 6. 对外同步口径

5 月 20 日经营看板 GMV 因订单状态枚举同步不完整出现偏低，数据团队已完成修复和补数。当前看板数据已恢复，可按最新数据继续使用。
```

## 使用说明

这个示例展示如何写清影响、时间线、根因和预防措施，同时保持复盘语言中性。
