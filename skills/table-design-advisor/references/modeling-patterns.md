# 建模模式

这里的做法是常见选择，要结合查询场景、数据量和团队规范判断。

## 怎么选表类型

| 需求 | 选择 | 代价 |
| --- | --- | --- |
| 记录每一次业务事件 | 事务事实表 | 历史状态需要关联其他表 |
| 看某一时点的状态 | 周期快照表 | 存储随时间增长 |
| 跟踪一个流程的多个里程碑 | 累积快照表 | 需要回写历史分区 |
| 维度低频变化，要查历史值 | 拉链表 | 写入和查询都更复杂 |
| 看板要查得快 | 宽表或汇总表 | 上游变更影响面大 |

## 更新策略

| 策略 | 适用 | 注意 |
| --- | --- | --- |
| 增量追加 | 事件不会变化 | 晚到数据要回补最近几个分区 |
| 增量覆盖 | 状态会变化，变化范围可控 | 明确回溯窗口 |
| 全量快照 | 维表、小表 | 存储成本；保留周期要明确 |
| 拉链 | 维度变化少，要查历史 | 重跑成本高，要有修复方案 |

## 拉链表要点

- 字段：业务键、`start_date`、`end_date`，当前有效记录的 `end_date` 用固定的最大日期。
- 查询：`where start_date <= :d and end_date > :d`，边界开闭要统一并写进文档。
- 校验：同一业务键的区间不能重叠，也不能断档。
- 重跑：错误修复通常要从出错日期开始全部重算。

## 粒度

- 先用一句话写出“一行代表什么”。写不出来就不要往下设计。
- 同一张表不要混粒度，比如订单和订单行放在一起。
- 宽表主键仍要明确，宽表不是没有粒度。

## 分区

- 事实表按业务日期分区，并明确是事件时间还是入仓时间。
- 分区数和单分区大小要匹配引擎，避免小文件。
- 下游过滤条件要能命中分区字段。

## 字段

- 金额用定点数，币种和单位写进字段注释。
- 状态字段写清枚举值和流转。
- 时间字段写清时区和含义。
- 审计字段：创建时间、更新时间、ETL 批次。
- 不用 `flag1`、`ext` 这种无法理解的命名。

## 什么时候不要加这一层

- 只有一个下游、查询简单时，不要提前做 DWS 汇总。
- 指标口径还在频繁变化时，不要把口径固化进宽表。
