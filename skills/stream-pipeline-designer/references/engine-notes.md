# 引擎与接入方式

设计前先确认引擎和版本。这里列的是选型时要问的问题，具体配置项以所用版本的官方文档为准。

## Flink

- 适合低延迟、复杂状态和事件时间处理。
- 状态后端：内存型状态快但受堆大小限制，RocksDB 支持大状态和增量 Checkpoint。Flink 2.x 引入了基于远端存储的状态后端，使用前确认版本和成熟度。
- 无界 Join 和聚合必须设置 State TTL。
- Exactly-once 依赖 Checkpoint 和下游事务或幂等写入。

## Spark Structured Streaming

- 默认微批，延迟通常在秒级，适合已有 Spark 技术栈、延迟要求不苛刻的场景。
- 用 `withWatermark` 限制状态增长，迟到数据超过水位后会被丢弃。
- 状态存储可选 RocksDB，大状态时优先考虑。
- 写入语义取决于 Sink，`foreachBatch` 里要自己保证幂等。
- 输出模式（append、update、complete）决定下游收到什么，和窗口语义有关。

## Kafka Streams

- 作为库嵌入应用，不需要独立集群，适合 Kafka 到 Kafka 的轻量处理。
- 状态存在本地并由 changelog Topic 备份，恢复时间取决于状态大小。
- 分区数决定并行度上限，上线后调整代价大。

## CDC（数据库变更捕获）

- 常见方案是基于 binlog 或 WAL 的 Debezium、Flink CDC。
- 全量快照阶段和增量阶段的衔接要确认：是否无锁、断点能否续传。
- 消息带更新前后的镜像时，下游要处理更新和删除，不能当成追加流。
- DDL 变更如何传播要提前设计。
- 主键更新、分库分表合并、大事务都要单独验证。
- 源库压力：binlog 保留时长要大于最长故障恢复时间。

## 选型参考

| 需求 | 倾向 |
| --- | --- |
| 秒级以下延迟，复杂状态或事件时间逻辑 | Flink |
| 秒级到分钟级，已有 Spark 团队 | Spark Structured Streaming |
| Kafka 内部轻量转换 | Kafka Streams |
| 数据库实时同步 | CDC 接入后再选计算引擎 |

## 实时和离线对齐

- 明确边界：实时结果在 T+1 后是否被离线结果覆盖。
- 统一时区和归属时间，否则两边的日期永远对不上。
- 对账指标写进质量规则，差异超过容差时告警。
- 准备补数方案：回放 Kafka、重算离线，或写入修正数据。
