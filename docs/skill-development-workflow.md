# Skill 开发工作流

这份文档是 [SOP.md](../SOP.md) 的详细版本，适合开发或评审一个新 Skill 时逐步使用。

## 阶段一：需求澄清

目标：确认这个 Skill 是否值得做。

检查问题：

- 这是数据开发、数据分析、数据治理、汇报表达还是职业成长场景？
- 这个动作是否高频？
- 用户是否经常做错或返工？
- 它是否能被一个 Agent 独立执行？
- 它是否有明确输出？

不通过条件：

- 只有知识解释，没有操作流程
- 输出无法检查
- 输入不稳定且无法模板化
- 依赖不可公开的公司规则

## 阶段二：边界定义

目标：避免 Skill 过大。

必须定义：

- 这个 Skill 负责什么
- 这个 Skill 不负责什么
- 哪些任务应该转给其他 Skill

例如：

```text
sql-reviewer 负责 SQL 审查。
它不负责从零澄清业务需求，也不负责完整表设计。
```

## 阶段三：上下文契约

目标：说明 Agent 需要什么信息才能工作。

上下文分三层：

- L0：最小上下文，能启动
- L1：推荐上下文，能给出可靠建议
- L2：丰富上下文，接近真实交付

每个 Skill 至少要写清：

- 最少输入
- 推荐输入
- 信息不足时如何降级
- 应使用哪个上下文模板
- 是否需要行业上下文包

## 阶段四：输出标准

目标：让输出能被用户直接使用。

输出模板必须明确：

- 结论
- 依据
- 风险
- 建议
- 待确认问题
- 下一步

不同 Skill 可以有不同结构，但不能只有泛泛建议。

## 阶段五：示例设计

目标：让用户一眼看懂怎么用。

示例不要太复杂。

好的示例应该：

- 场景真实
- 数据脱敏
- 输入完整但不过度
- 预期输出展示关键结构
- 能暴露 Skill 的价值

## 阶段六：测试设计

目标：证明 Skill 至少能被稳定评测。

每个 Skill 至少一条测试用例。

测试用例要包含：

- Skill 名称
- 测试目标
- 测试输入
- 通过标准

通过标准要具体，不能写“输出合理即可”。

## 阶段七：自动检查

运行：

```bash
node scripts/check-library.mjs
node scripts/check-tests.mjs
```

如果涉及 mock 数据：

```bash
node scripts/summarize-ecommerce-fixture.mjs
```

检查失败时，先修结构，再讨论内容。

## 阶段八：人工评测

人工评测不是为了证明自己写得好，而是为了发现 Skill 的模糊点。

重点看：

- 是否误解任务
- 是否忽略上下文
- 是否编造事实
- 是否给出不可执行建议
- 是否越界处理其他 Skill 的任务

## 阶段九：入库维护

新增 Skill 合并后，必须能被用户找到。

检查：

- README 是否有分类
- SKILL_INDEX 是否有入口
- examples/README 是否有示例链接
- tests/README 是否有测试覆盖
- CONTEXT_GUIDE 是否需要更新
- context/README 和 context/industries/README 是否需要更新

## 完成定义

一个 Skill 完成，不是指 `SKILL.md` 写完。

完成定义是：

- Skill 本体可用
- 上下文契约清楚
- 示例可读
- 测试可跑
- 索引可找到
- 贡献者知道如何继续维护
